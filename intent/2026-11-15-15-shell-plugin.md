# Intent: an Omarchy shell plugin for llm-index status and settings

## Problem

llm-index runs as a background user service on p620 and razer with no desktop
interface. Status comes only from `llm-index status` in a terminal, or from the
MCP `status` tool an agent calls. The effective configuration is a read-only
`config.toml` generated by Home Manager. So nothing on the desktop shows that:

- the service has stopped or failed;
- a root is `offline`, `degraded` or `config_error`. On p620, `source` was
  offline with `identity mismatch` from 2026-11-14 (#14), and nobody noticed
  until a manual `llm-index status`;
- a first index is still running, and how far it has got;
- which settings are in effect (roots, tiers, limits, exclusions).

`llm-index status` takes about 3 s per call on p620's 1.4 GB public database
(measured 2026-11-15), so a surface that polls it naively would load the
machine.

## Proposed outcome

An Omarchy shell plugin, following the Omarchy plugin guide
(`nixarchy/docs/manual/plugins.md`) and the first-party `rebuild-panel` pattern:

- **Bar widget** that draws only when something needs attention: the service
  is stopped or failed, a root is not `ok`, or indexing is in progress. It opens
  a keyboard-driven panel. A shell **menu** entry opens the same panel when
  the widget is hidden.
- **Status view:** the service state, each root with its tier, state, reason,
  last scan, queued/done, files and chunks, the sandbox line, and database
  sizes.
- **Settings view:** a read-only, path-free summary of the effective config
  (roots by name, tier and kind, intervals, limits, the number of exclusions),
  with a "managed by Nix" hint naming where to change it.
- **Actions:** Refresh, Restart service (confirmed), Run self-test, Open log in
  a terminal.
- `llm-index status --json` as the machine-readable source. The plain-text
  `status` output stays as it is.
- Installed and enabled on p620 and razer through nixos_config.

## Affected users and systems

- This repository: the CLI (`src/main.rs`, `src/status.rs`), a new plugin
  directory, the flake outputs and checks, and the docs.
- nixos_config: `hosts/common/nixos/llm-index.nix` (plugin install via
  `programs.nixarchy.plugins`), and the flake input bump. Hosts: p620 and razer.
- The owner, at the desktop. Agents are not users of the plugin.

## Constraints

- **Settings stay declarative.** The plugin never writes `config.toml`, a
  runtime override, or nixos_config. Changing roots, tiers or exclusions stays
  a reviewed Nix change.
- **The private tier never leaves the panel.** Private-root counts show only
  inside the open panel, never in the bar tooltip, shell IPC replies, logs or
  notifications. No file paths, titles or contents from the index are shown;
  the plugin never calls `search`, `get` or `recent`.
- **Untrusted text is plain text.** Root reasons and any string from the index
  or config render with `Text.PlainText`. Qt's default AutoText fetches
  `<img src=…>` (see the herdr plugin's note).
- **Cheap when closed.** With the panel closed, the plugin polls only the
  systemd unit state and does not open the databases. The heavy status call
  runs on panel open, on Refresh, and at a slow rate while the panel is open.
  The exact rates go in the spec, measured on p620 and razer.
- **No new daemon surface.** No control socket and no pause or reindex in this
  task. Stopping the service is not presented as "pause".
- **Omarchy conventions.** Theme and keyboard handling come from the shell's
  shared UI components. No external writer for `shell.json`, which breaks
  bar IPC (`nixarchy/docs/internals/shell-json-reload.md`).
- The usual rules: agents don't commit or deploy. p510 is out of scope.

## Open questions

1. **Plugin ID.** `olafkfreund.llm-index` (your own plugins' namespace,
   such as `olafkfreund.gmessages`) or `nixarchy.llm-index` (the first-party
   namespace)? The draft assumes `olafkfreund.llm-index`.
2. **Order against #14.** #14 (a root goes offline after the machine restarts,
   because its identity uses `/dev/sdX`) breaks p620's code search today. The
   draft assumes #14 is fixed first, as a separate task, and that this plugin
   then shows that kind of failure.
